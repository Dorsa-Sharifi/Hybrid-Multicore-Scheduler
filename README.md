# Hybrid Scheduling for Multi-Core Embedded Systems (Partitioned-EDF + TBS)

A discrete-event simulator and experiment suite for **Embedded Systems Project**: hybrid
scheduling of hard periodic tasks and soft aperiodic jobs on homogeneous
multi-core embedded systems, comparing **Partitioned-EDF + Total Bandwidth
Server (TBS)** against a **Background scheduling** baseline.

## What's implemented

- **Offline partitioning**: periodic tasks assigned to cores via
  **Worst-Fit-Decreasing (WFD)** on utilization, feasibility-checked against
  `U_core <= 1`.
- **Online TBS**: each core reserves aperiodic bandwidth `U_s,j = 1 - U_periodic,j`.
  On arrival, an aperiodic job's virtual deadline is computed on *every* core
  via `V_d,j = max(A_k, V_d,prev,j) + E_k / U_s,j`, and it is dispatched to the
  core minimizing `V_d,j` (global TBS allocation → load balancing).
- **EDF runtime** on each core: the ready job with the earliest deadline runs
  (periodic jobs use real absolute deadlines; aperiodic jobs use their TBS
  virtual deadline). Preemption is immediate when a shorter-deadline job
  becomes ready.
- **Migration**: when a running aperiodic job is preempted, its virtual
  deadline is *re-evaluated* across all cores using its *remaining* execution
  time; if another core now offers a strictly smaller deadline, the job
  migrates there (bounded to at most `m` hops per event to avoid cascades).
- **Background baseline**: identical periodic EDF scheduling; aperiodic jobs
  are given deadline `+inf` (i.e., they only run when no periodic job is
  ready on that core) — no TBS bandwidth reservation.
- **Workload generators**: **UUniFast** for periodic utilizations, discrete
  period set `{10,20,50,100,200,500,1000} ms`, **Poisson** aperiodic arrivals
  with **Exponential** job sizes.
- **Experiment harness**: runs `NUM_SEEDS` (default **100**, matching the spec's
  "≥100 unique task sets per configuration") independent random task sets per
  configuration and averages results.
- **5 required plots** (see `figures/`), generated by `run_experiments.py`.

## How to run

```bash
# from the project root
python3 run_experiments.py
```

This runs both experiment campaigns (~30s total on a modern machine) and
(re)writes everything in `figures/` and `results/raw_results.json`.

To run a single one-off simulation (e.g., for debugging):

```python
from sim.experiments import run_one_seed
result = run_one_seed(n=16, u_p=0.5, m=4, u_a=0.2, seed=1, policy="tbs")
print(result)
```

## Experiment design (which configs feed which plot)

Two campaigns cover all 5 plots without redundant simulation:

**Campaign A ("N-sweep")** — feeds **Plot 1**:
`m ∈ {2,4,8}`, `N ∈ {10,20,30,40}`, `U_p = 0.5`, `U_a = 0.2`, policy = TBS.

**Campaign B ("U_a-sweep")** — feeds **Plots 2, 3, 4, 5**:
`m = 4`, `N = 16 (= 4m)`, `U_p = 0.5`, `U_a ∈ {0.05, 0.10, ..., 0.40}`,
policy ∈ {TBS, Background}.
- Plot 2: mean aperiodic response time, TBS vs Background, vs `U_a`.
- Plot 3: per-core total utilization (periodic + aperiodic), TBS only, vs `U_a`.
- Plot 4: periodic deadline miss rate, both policies, vs `U_a`.
- Plot 5: average migrations per run, TBS only, vs total load `U_p + U_a`
  (same x-axis data as Plot 2/4, just relabeled + a different y-metric).

Each `(config, seed)` draws one independent periodic task set (regenerated up
to `MAX_PARTITION_ATTEMPTS` times if WFD partitioning is infeasible) and one
independent Poisson aperiodic arrival stream; the *same* periodic task set is
reused across the TBS and Background runs for a given seed, so the
policy comparison in Plot 2/4 is apples-to-apples.

## Decisions made where the spec was underspecified

The spec (`CLAUDE.MD`) explicitly flags these as open — here is what this
implementation chose and why:

1. **Normalization for Plot 1**: normalized response time = mean aperiodic
   response time ÷ `E[E_k]` (mean aperiodic job execution time, 5 ms by
   default). This is the standard normalization in the aperiodic-server
   literature since it expresses delay in units of "job sizes" rather than
   raw ms, making curves comparable across different mean-execution-time
   assumptions.
2. **Rounding for `C_i = U_i · P_i`**: rounded to 3 decimal places (i.e.
   microsecond resolution given periods in ms), clamped to a 0.001 ms
   minimum so no task has zero execution time. The simulator uses
   floating-point time throughout, so no ms-tick quantization error is
   introduced elsewhere.
3. **Aperiodic execution-time distribution**: Exponential with mean 5 ms
   (`MEAN_APERIODIC_EXEC` in `generators.py`), clamped at 0.1 ms minimum.
   Exponential job sizes are the natural pairing with Poisson arrivals for a
   memoryless M/M/1-style aperiodic load model.
4. **Simulation horizon**: fixed at `HORIZON_MS = 3000` ms per run (see
   `sim/config.py`), no explicit warmup — deadline-miss / response-time
   statistics are collected over the full horizon. With periods up to
   1000 ms this gives every periodic task at least 3 full periods, and with
   100 seeds/config the aggregate curves are already smooth (see
   `results/raw_results.json`).
5. **Migration rule**: an aperiodic job is only re-evaluated for migration
   at the moment it is *preempted* (not on every arrival, and not while it's
   the one running). It migrates only if some other core now offers a
   strictly earlier recomputed virtual deadline (using its *remaining*
   execution time). This mirrors "preemption → re-evaluate → possibly
   migrate" from the spec while keeping the TBS bandwidth-reservation
   invariant intact (see next section for why this matters).

## A real bug we caught via the Plot 4 sanity check

Plot 4 requires periodic deadline miss rate to be **exactly 0%** — this is
the built-in correctness check that TBS integration never violates hard
real-time guarantees. An early version of the migration logic reassigned a
displaced aperiodic job to a new core and immediately called `_reschedule()`
there *without first advancing that core's clock/current-job bookkeeping to
the current time*. That left a stale `remaining` value on whatever job was
running on the destination core, which occasionally delayed a periodic job's
actual completion by ~1 ms past its deadline (observed miss rate ≈0.001% at
high load). The fix: always call `_advance_core()` + `_finish_check()` on the
destination core *before* inserting the migrated job. Verified with 300
extra seeds at the worst-case configuration (`U_a=0.40, m=4`) after the fix:
**0 misses out of 379,998 periodic jobs**. This is exactly the kind of thing
Plot 4 is designed to catch.

## Reproducibility

- All randomness flows through Python's `random.Random(seed)` with explicit,
  deterministic per-configuration seeds (see `sim/experiments.py`) — re-running
  `run_experiments.py` reproduces identical figures and `raw_results.json`.
- To reproduce with a different seed count (e.g. to stress-test further),
  change `NUM_SEEDS` in `sim/config.py`. At ~15-20 ms/run worst-case, even
  1000 seeds/config completes in a few minutes.
